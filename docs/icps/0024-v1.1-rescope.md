# ICP 0024: v1.1 rescope — hot reload without a socket

**Status:** Accepted — decided 2026-09-14; the amendments below are applied in
this PR.
**Affected interfaces / docs:** `microtel-roadmap.md` §4 (v1.1 block), §6
(footprint trajectory), §7 (adoption story), §8 (anti-goals), §9
(documentation), §10 (decision log); `microtel-spec.md` §8 (deferral table),
§10.5 (footprint targets), §18.1, §19 (threat model). No interface headers, no
`docs/interfaces.md`, no code, no CI.
**Affected tracks:** none — release scope and documentation only.

## Summary

v1.1 ships hot reload as four thread-safe `Provider` setters; the
control-plane socket, `microtelctl`, and the threat model that prices them move
to **v1.2**. OAuth2 and SigV4 become documented `AuthCallback` recipes rather
than built-in providers, the promised sample-on-duration combinator is
withdrawn as impossible for a head sampler, and the v1.1 ships-when gate is
replaced with a five-clause version that tests the feature set that actually
ships.

## Motivation

**The control plane is designed, priced, and not worth its price in v1.1.**
[`docs/control-plane-design.md`](../control-plane-design.md) is complete and
its own disposition note explains why it is not being built: the socket would
be the project's first inbound socket, a fourth thread, a hand-written parser
on attacker-adjacent input, a signal handler, a permanent threat model, and an
administrative surface frozen under spec §19's compatibility policy — for a
user-visible capability of **four knobs adjustable without a restart**. That
document's §2 closing alternative (*"Alternative: expose the reloadable knobs
as ordinary public setters"*, `docs/control-plane-design.md:290-314`) records
thread-safe `Provider` setters — `SetBatchOptions`, `SetMetricInterval`,
`SetSamplerRatio`, `SetLogLevel` — as the **leading candidate to evaluate
first** if M15 is ever revisited. This ICP evaluates it and takes it. The
setters deliver the four knobs with no socket, no parser, no fourth thread, no
signal handling, and no threat model; what they do not deliver, stated as
plainly as the design doc states it, is **out-of-process administration** — an
operator can reach them only through a control surface the host application
already has. That is a smaller feature, and v1.2 is where the larger one is
re-priced against real deployment feedback.

**OAuth2 and SigV4 need no code in the runtime.** Spec §12.5 already ships
`WithAuthProvider(callable)` — called per export batch, results cached for a
configurable TTL — and `docs/compatibility-matrix.md` records it as supported
and tested. A built-in OAuth2 provider is an HTTP client for a token endpoint;
a built-in SigV4 provider is a request-signing implementation. Both are
reachable today through the callback, and shipping them in-tree buys the user
nothing the callback lacks while adding runtime surface to a project whose
pitch is the absence of it. They become documented recipes, landing with the
v1.1 documentation pass.

**Sample-on-duration cannot be built at the head.** `ISampler::ShouldSample`
is called on the caller thread at span start
([`docs/interfaces.md`](../interfaces.md) §4.5) — the span has not run, so its
duration does not exist yet. Selecting spans by how long they took is tail
sampling: it needs a buffer of completed spans and a decision point after the
fact, which is the collector's job in every deployment microtel targets. The
roadmap has promised it since v0.9 and it was never implementable; correcting
the text is cheaper than discovering this in v1.1 implementation.

**The old gate tests two features that no longer ship.** *"sugar layer has a
stable API, control plane has a documented threat model, hot reload is
fuzz-tested"* — the middle clause prices a socket that moves to v1.2, and the
third was written against that socket's parser.

### The amended gate

> **Ships when:**
> 1. The sugar layer has a stable API, recorded in ICP 0028 and shipped as installed headers.
> 2. The hot-reload setters pass a TSAN-built concurrent hammer test — all four setters racing span/log emission, the BSP/BLRP workers, and metric collection — and their input validation is fuzz-tested by a harness driving randomized values and interleavings against a live provider in the standing fuzz job.
> 3. The propagation core passes W3C test vectors for traceparent, tracestate, and baggage, including grammar limits, and the baggage header parser has a fuzz target.
> 4. Roadmap and spec are amended for the socket/microtelctl deferral (threat-model + hot-reload-socket-fuzz gates move with it to v1.2), the OAuth2/SigV4 → AuthCallback-recipes substitution, and the sample-on-duration correction.
> 5. Every issue on the v1.1 milestone is closed or explicitly re-milestoned with a recorded reason.

**Why clause 2 reads the way it does.** The old gate's threat-model clause
priced the socket's attack surface and its fuzz clause priced that socket's
parser. The setters have neither, so the threat-model clause travels to v1.2
with the thing it was written about. The reload risk the fuzz clause stood in
for does not disappear, though — it changes shape: with setters it is **data
races between setter writers and hot-path readers**, which a fuzzer does not
find and TSAN under contention does. Hence the hammer test. The fuzz clause
survives in reduced, honest form because the setters keep a real validation
surface — value ranges, batch-size/queue-depth coherence, a ratio setter
called on a sampler that is not a `TraceIdRatio` — and the fuzz job already
exists, so the marginal cost is a harness. Nothing the old wording tested for
the shipped feature set goes untested, and nothing is claimed for a feature
that no longer ships. Clause 4 is this ICP; it is listed because a gate that
cannot be checked off from the repository is not a gate.

## Migration

- **Contributors and agents:** v1.1 hot reload is four `Provider` setters. Do
  not build the socket, the JSON wire, or `microtelctl` against the v1.1
  milestone.
- The four setters are a public-API addition and get their own ICP when their
  signatures are drafted; this ICP schedules them, it does not lock them.
- No code, interface, test, or CI changes. Nothing to rebuild.

## Rationale & alternatives

- **Ship the socket in v1.1 as written** — rejected for the reasons the design
  doc already records, which have not changed: no users in production, nothing
  packaged (M10 unshipped), and an administrative surface frozen on first
  release under §19.
- **Ship the setters *and* the socket in v1.1** — rejected. The setters are
  the socket's own reload mechanism; building both at once means designing the
  socket around an API that has no operational feedback behind it either.
- **Defer hot reload entirely to v1.2** — rejected. The four knobs are the
  part of M15 with demonstrated incident-response value, and the setter form
  costs a fraction of the socket. Deferring the cheap half with the expensive
  one buys nothing.
- **Ship built-in OAuth2 / SigV4 anyway** — rejected. Adapter packages remain
  available (spec §12.5 already says so); the recipes make the supported path
  discoverable without putting a token client and a request signer in the
  runtime.
- **Silently drop the sample-on-duration phrase** — rejected. The roadmap has
  promised it since v0.9; the correction says why it is not coming, which is
  the point of a roadmap that is read as a commitment.

## Related, not proposed here

- **[`docs/control-plane-design.md`](../control-plane-design.md) is not
  amended.** It remains the accurate design record for the socket, now aimed
  at v1.2, and its status note already declares its divergence from the spec
  deliberate. Two of the three ICPs it calls for die with the v1.1 socket
  slot: **§3** (asymmetric wire format) and **§5** (`microtelctl` in C++ rather
  than Go) are decisions about a component that is no longer scheduled, and
  are re-opened when the socket is. **§9** (the fourth thread role, a
  `docs/threading-model.md` amendment) survives on its own merits and is filed
  as forthcoming **ICP 0027**; the setters touch the threading model whether or
  not a socket ever exists.
- **`SetMetricInterval` is one of the four because the design doc's tiering
  names it**, and metrics exist as-built (M12/M13) even though the roadmap
  schedules the metrics *release* at v1.2. On a provider with no meter
  configured the setter is inert. The v1.1 "still no metrics" anti-goal is a
  statement about release content and is left untouched.
- **Spec §13's M15 row is not amended.** It still describes the socket build,
  which is now v1.2 work; the four setters are not a milestone-sized
  deliverable. Whether M15 is split or simply travels intact is left to v1.1
  milestone planning rather than decided here.
